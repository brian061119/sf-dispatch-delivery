## 问题1：按「耗时最短」选择配送站，且按载具类型逐站兜底

### 需求

选择耗时最短的配送站，判断标准为**配送站分别到起点和终点的距离之和最小**。
若耗时最短的配送站没有顾客需要的机器人/无人机，则寻找耗时第二短的，以此类推。
判断前提是**顾客选择的是机器人还是无人机**（例如顾客选无人机，但耗时最短的站无法派送无人机，则寻找耗时第二短的站，以此类推）。

### 改动前

`selectBestStation(...)` 只按「站点到**取件点**的直线距离」选出**唯一一个**站，随后无人机方案与机器人方案**共用**这个站：

```java
private Station selectBestStation(List<Station> stations, QuoteRequest request) {
    if (Boolean.TRUE.equals(request.getIsStationPickup()) && request.getStationId() != null) {
        return stations.stream()
                .filter(s -> s.getId().equals(request.getStationId()))
                .findFirst()
                .orElse(stations.get(0));
    }
    // 寻找离取件地最近的站点
    double pLat = request.getPickupLat().doubleValue();
    double pLng = request.getPickupLng().doubleValue();
    return stations.stream()
            .min(Comparator.comparingDouble(s ->
                    routeService.calculateStraightDistance(
                            s.getLatitude().doubleValue(), s.getLongitude().doubleValue(),
                            pLat, pLng)))
            .orElse(stations.get(0));
}
```

### 改动后

1. **候选站点排序**：按「站点→起点 + 站点→终点」的直线距离之和升序（即需求给定的判断标准）。
2. **按类型逐站查找**：对无人机、机器人分别沿该顺序逐站做完整准入，返回**首个能派发该类型**的站点；耗时最短的站不可派发时自动退到次优站，以此类推。
3. 顾客若自投并指定站点，则只考虑该站点（不兜底）。

新增/替换的方法（`RecommendationService.java:110-158`）：

```java
/**
 * 候选服务分配站：
 *   1. 顾客自投并指定站点时，仅该站点参与；
 *   2. 否则按「站点→起点 + 站点→终点」直线距离之和升序排列，
 *      作为「耗时最短优先」的候选顺序，供逐站兜底查找。
 */
private List<Station> candidateStations(List<Station> stations, QuoteRequest request) {
    if (Boolean.TRUE.equals(request.getIsStationPickup()) && request.getStationId() != null) {
        List<Station> forced = stations.stream()
                .filter(s -> s.getId().equals(request.getStationId()))
                .collect(Collectors.toList());
        if (!forced.isEmpty()) {
            return forced;
        }
    }

    double pLat = request.getPickupLat().doubleValue();
    double pLng = request.getPickupLng().doubleValue();
    double dLat = request.getDropoffLat().doubleValue();
    double dLng = request.getDropoffLng().doubleValue();

    return stations.stream()
            .sorted(Comparator.comparingDouble(s -> distanceToTrip(s, pLat, pLng, dLat, dLng)))
            .collect(Collectors.toList());
}

/** 站点到起点与终点的直线距离之和（km）——配送站耗时排序的判断标准 */
private double distanceToTrip(Station station, double pickupLat, double pickupLng,
                              double dropoffLat, double dropoffLng) {
    double lat = station.getLatitude().doubleValue();
    double lng = station.getLongitude().doubleValue();
    return routeService.calculateStraightDistance(lat, lng, pickupLat, pickupLng)
            + routeService.calculateStraightDistance(lat, lng, dropoffLat, dropoffLng);
}

/**
 * 按候选顺序逐站做该类型载具的全量准入，返回首个能派发的站点筛选结果；
 * 耗时最短的站点无可用载具时自动退到次优站点，全部站点都不可派发时返回 null。
 */
private Candidate selectForType(List<Station> candidateStations, QuoteRequest req,
                                VehicleType type, boolean isVip) {
    for (Station station : candidateStations) {
        Candidate candidate = evaluate(req, station, type, isVip);
        if (candidate != null) {
            return candidate;
        }
    }
    return null;
}
```

`generateRecommendations(...)` 主流程改为**按类型各自选站**（`RecommendationService.java:78-100`）：

// 1. 方案一：Fastest (无人机极速达)，逐站寻找首个可派发无人机的站点

配套的签名调整：

- `Candidate` 内部类新增 `station` 字段，`evaluate(...)` 中写入 `candidate.station = station;`。
- `buildOption(...)` 去掉 `Station station` 形参，改用 `candidate.station`。
- `evaluateOffPeakOption(...)` 去掉 `Station station` 形参，改用 `basePlan.getStationId()/getStationName()`（错峰方案跟随基准方案的站点，基准方案可能是机器人、也可能是退化后的无人机）。

**失败用例：** `MachineAccessApiTest.rejectsInvalidPayloads`

**现象：** 向 telemetry 上报越界电量 `{"batteryLevel":150}` 时，期望 HTTP `400`，实际返回 `500`。

```
java.lang.AssertionError: Status expected:<400> but was:<500>
    at com.wedelivery.MachineAccessApiTest.rejectsInvalidPayloads(MachineAccessApiTest.java:137)
```

**判定为改动前既有问题，与本次两项需求无关的证据：**

1. 该用例走 `/api/dispatch/vehicles/{code}/telemetry` → `VehicleService`，`VehicleTelemetryRequest` 上声明了
   `@DecimalMax(value = "100.00", message = "电量不能超过 100")`，属于**参数校验异常未映射成 400** 的问题。
2. `VehicleService` 完全未引用 `RecommendationService`；本次改动只落在 `RecommendationService.java` 一个文件，
   不可能影响该路径。

**结论：** 该问题属于「机器接入」入口的参数校验异常映射，超出本次两项需求范围，**本次不修改**，仅在此备案，待后续单独处理。
