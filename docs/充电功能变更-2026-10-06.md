# 充电功能变更记录（2026-10-06）

本次改动实现「机器充电需要时间」的完整闭环：行程真实耗电 → 返站自动充电 → 充满再待命，
并把充电中的载具纳入派单候选池（电量够即可抽调），同时把派单的选车规则由「电量最高」改为「电量最低」。

- **未新增任何代码文件**，全部为对既有文件的修改。
- **修改文件（6 个主代码）**
  - `server/src/main/java/com/wedelivery/entity/Vehicle.java`
  - `server/src/main/java/com/wedelivery/repository/VehicleRepository.java`
  - `server/src/main/java/com/wedelivery/service/RecommendationService.java`
  - `server/src/main/java/com/wedelivery/service/OrderService.java`
  - `server/src/main/java/com/wedelivery/service/TrackingService.java`
  - `server/src/main/java/com/wedelivery/service/SimulationService.java`
- **修改文件（2 个测试，因语义变更同步）**
  - `server/src/test/java/com/wedelivery/AuthAndAdminApiTest.java`

## 需求与设计决策

需求要点：

1. 机器充电需要时间，要纳入并实现；载具状态栏的 `CHARGING` 要有真实的充电过程。
2. 有配送订单时判断电量需求：`现有电量 − 一整个配送流程耗电 > 10%` 才允许配送，否则不配送。
3. 默认在配送站充电。
4. 起点、终点、配送站已确定时，在满足机型与电量需求的前提下，**优先派遣电量低的**载具。

落地方案经确认采用以下三条决策（改动前 `CHARGING` 状态虽已存在，但没有任何流程会进入该状态，
且订单全程不扣电，充电基本触发不到）：

| 决策点 | 采用方案 |
|---|---|
| 何时进入 `CHARGING` | 配送返站后自动进入：电量未满即 `CHARGING`，按 tick 补电，充满转 `IDLE` |
| 行程是否扣电 | 是：按「里程 × 能耗率 × 载重加权」真实扣减 |
| 充电中能否被派单 | 能：只要 `现有电量 − 全程耗电 ≥ 10%` 即可临时抽调 |

## 改动明细

### 1. `Vehicle.java` —— 新增满电常量与「返站默认状态」

新增常量（`Vehicle.java:25`）：

```java
/** Full battery level (%). */
public static final BigDecimal FULL_BATTERY = new BigDecimal("100.00");
```

新增派生方法（`Vehicle.java:117-125`）——「返站默认在配送站充电」的唯一真源，
`TrackingService` / `SimulationService` / `OrderService` 三处返站都调用它：

```java
/**
 * 停回站点后的默认状态：电量未满即 CHARGING（由模拟器逐 tick 补电，充满再转 IDLE），满电则直接 IDLE。
 * 充电需要时间，故返站不会瞬间回满待命。
 */
public VehicleStatus restingStatus() {
    return batteryLevel != null && batteryLevel.compareTo(FULL_BATTERY) < 0
            ? VehicleStatus.CHARGING
            : VehicleStatus.IDLE;
}
```

### 2. `VehicleRepository.java` —— 候选池与锁定查询支持「待命 + 充电」且电量升序

新增集合查询（`VehicleRepository.java:23-24`）：

```java
/** 站内某类型、状态属于给定集合的载具（派单候选池：待命 + 充电）。 */
List<Vehicle> findByStationIdAndVehicleTypeAndStatusIn(Long stationId, VehicleType vehicleType, Collection<VehicleStatus> statuses);
```

下单锁车查询由「单状态 `=` + 电量降序」改为「状态集合 `IN` + 电量升序」（`VehicleRepository.java:34-51`）。
升序与「优先派电量低」一致，保证推荐结果与实际锁定的载具是同一台（电量最低的合格车）：

```java
// Ordered by batteryLevel ASC so the most depleted eligible vehicle is dispatched first (fleet balancing).
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT v FROM Vehicle v WHERE v.stationId = :stationId " +
       "AND v.vehicleType = :vehicleType " +
       "AND v.status IN :statuses " +
       "AND v.batteryLevel >= :minBattery " +
       "AND v.maxWeight >= :weight " +
       "AND v.maxVolume >= :volume " +
       "ORDER BY v.batteryLevel ASC")
List<Vehicle> findAvailableVehiclesForLock(
        @Param("stationId") Long stationId,
        @Param("vehicleType") VehicleType vehicleType,
        @Param("statuses") Collection<VehicleStatus> statuses,   // 原为单个 VehicleStatus status
        @Param("minBattery") BigDecimal minBattery,
        @Param("weight") BigDecimal weight,
        @Param("volume") BigDecimal volume
);
```

### 3. `RecommendationService.java` —— 候选池含充电车 + 优先派电量低 + 共用耗电系数

新增派单候选状态常量（`RecommendationService.java:57-59`）：

```java
/** 派单候选状态：待命与充电中的载具都可被抽调。 */
public static final List<VehicleStatus> DISPATCHABLE_STATUSES =
        Collections.unmodifiableList(Arrays.asList(VehicleStatus.IDLE, VehicleStatus.CHARGING));
```

新增载重加权系数方法（`RecommendationService.java:79-88`）。派单准入与行程实际扣电共用它，
实现「预测耗电 = 真实耗电」：

```java
/**
 * 载重对能耗的加权系数：空载为 1.0，满载为 1 + LOAD_WEIGHT_FACTOR_SPAN。
 * 派单准入与行程实际扣电共用同一系数，保证「预测耗电」与「真实耗电」一致。
 */
public static double loadWeightFactor(double packageWeight, double maxWeight) {
    if (maxWeight <= 0) {
        return 1.0;
    }
    return 1.0 + (packageWeight / maxWeight) * LOAD_WEIGHT_FACTOR_SPAN;
}
```

`calculateRequiredInitialBattery(...)` 内的系数改为调用该方法（`RecommendationService.java:102`），
不再内联重复公式。

`evaluate(...)`（`RecommendationService.java:204-250`）两处改动：

- **候选池**：由「仅 IDLE」改为「IDLE + CHARGING」（`RecommendationService.java:204-205`）：

  ```java
  // 改动前
  List<Vehicle> idle = vehicleRepository.findByStationIdAndVehicleTypeAndStatus(
          station.getId(), type, VehicleStatus.IDLE);

  // 改动后
  List<Vehicle> candidates = vehicleRepository.findByStationIdAndVehicleTypeAndStatusIn(
          station.getId(), type, DISPATCHABLE_STATUSES);
  ```

- **选车**：由「电量最高」改为「电量最低」（`RecommendationService.java:243-246`）：

  ```java
  // 起点、终点、站点已定的前提下，优先派电量最低的一台，让高电量载具留站兜底
  candidate.planned = admissible.stream()
          .min(Comparator.comparing(Vehicle::getBatteryLevel))   // 原为 .max(...)
          .orElse(admissible.get(0));
  ```

三重准入（载荷、续航 90% 冗余、电量）保持不变；其中电量准入即需求 2 的规则：
`v.getBatteryLevel() - energyDelta < MIN_RESERVE_BATTERY_PERCENT(10)` 则排除，
即 `现有电量 − 全程载重加权耗电 ≥ 10%` 才允许。

### 5. `TrackingService.java` —— 行程真实耗电 + 返站充电

新增依赖 `RouteService`（用于计算每 tick 的位移线段里程）。

`track(...)` 的机器同步块（`TrackingService.java:135-179`）新增两点：

1. **逐段扣电**：用载具上一位置与本次新位置算位移里程，按 `里程 × 类型能耗率 × 载重加权` 扣电；
   反复调用 `track` 时每次只扣「本次位移」，不会重复累扣。

   ```java
   // 行程实际耗电：按本次位移的直线里程 × 类型能耗率 × 载重加权，逐段累扣。
   // 与派单准入（RecommendationService）共用同一套耗电模型，故「预测耗电」与「真实耗电」一致。
   BigDecimal prevLat = vehicle.getCurrentLat();
   BigDecimal prevLng = vehicle.getCurrentLng();
   if (prevLat != null && prevLng != null) {
       double segmentKm = routeService.calculateStraightDistance(
               prevLat.doubleValue(), prevLng.doubleValue(),
               currentLat.doubleValue(), currentLng.doubleValue());
       if (segmentKm > 0) {
           double energyRate = vehicle.getVehicleType().getEnergyRatePercentPerKm().doubleValue();
           double weightFactor = RecommendationService.loadWeightFactor(
                   order.getPackageWeight() != null ? order.getPackageWeight().doubleValue() : 0.0,
                   vehicle.getMaxWeight() != null ? vehicle.getMaxWeight().doubleValue() : 0.0);
           BigDecimal drained = BigDecimal.valueOf(segmentKm * energyRate * weightFactor);
           BigDecimal nextBattery = vehicle.getBatteryLevel() == null
                   ? BigDecimal.ZERO
                   : vehicle.getBatteryLevel().subtract(drained);
           vehicle.setBatteryLevel(nextBattery.signum() < 0
                   ? BigDecimal.ZERO
                   : nextBattery.setScale(2, RoundingMode.HALF_UP));
       }
   }
   ```

2. **返站充电**：COMPLETED 航段返站时，`IN_DELIVERY` 的载具按电量进入 `CHARGING`/`IDLE`。

   ```java
   if (backAtStation) {
       vehicle.setCurrentSpeed(BigDecimal.ZERO);
       if (vehicle.getStatus() == VehicleStatus.IN_DELIVERY) {
           // 返站默认在配送站充电：电量未满转 CHARGING，由模拟器逐 tick 补电，充满再待命
           vehicle.setStatus(vehicle.restingStatus());
           vehicle.setStatusUpdatedAt(now);
       }
   }
   ```

## 完整闭环（改动后的行为）

```
下单锁车（电量最低的 IDLE 或 CHARGING 车）
   │  候选池 = 站内 IDLE + CHARGING；按电量升序取第一台
   │  电量准入：现有电量 − 全程载重加权耗电 ≥ 10%
   ▼
IN_DELIVERY：跟随 TrackingService 逐段推进，按位移真实扣电
   ▼
返站 COMPLETED：locationCode 归位，电量未满 → CHARGING（否则 IDLE）
   ▼
CHARGING：SimulationService.tick() 每 tick +10% 补电
   │  期间该车仍可被派单（电量够即抽调，抽调后转 IN_DELIVERY 停止充电）
   ▼
电量满 100% → IDLE
```

## 需要留意的两点

### 1. 跨模块文件

按项目惯例列出本次触碰的、非本模块独占的文件，供与对应同学对齐：

- `TrackingService.java`（追踪同学模块）：新增了电量扣减与返站充电状态。
- `OrderService.java`（订单同学模块）：锁车查询的状态集合、交付释放状态。

### 2. 刻意保留的不一致：`StationService` 的「可调度数」

站点实时信息（需求 2）的 `droneUnitsAvailable` / `robotUnitsAvailable` **仍只统计 `IDLE`**
（`StationService.buildAvailability`），有独立测试 `StationApiTest` 固化，本次未改动。
因此它现在比派单候选池（IDLE + CHARGING）**更窄**——即充电中的载具可被派单，但不计入需求量 2 的「可调度数」。

这是为避免改动需求 2 的既有语义与测试而刻意保留的。若后续希望需求 2 也把充电车计入，
需同时修改 `StationService` 与该测试的期望值。
