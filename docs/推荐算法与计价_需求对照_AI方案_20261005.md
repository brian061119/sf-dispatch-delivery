## 1. 推荐算法现状

### 1.1 五步主流程

```
用户输入 → SF边界校验+站点排序 → 三重准入 → 计价 → 输出三方案并打标
```

具体：

1. **输入**：起终点经纬度、重量 `weightKg`、体积（长宽高→m³）、是否站内自提。
2. **站点排序**：自提且指定站点时只用该站；否则按「站点→起点 + 站点→终点」直线距离之和升序，作为"耗时最短优先"的候选顺序。
3. **逐类型逐站找车**：先看 DRONE（方案 FASTEST），再看 ROBOT（方案 BEST_VALUE）；某个站没有可用车就退到次优站，全都没有则该方案不出现。
4. **计价**：见 §2。
5. **输出**：最多 3 个方案，打上 `isFastest` / `isCheapest` 标。

### 1.2 重量如何影响推荐（三个层面）

| 层面 | 代码逻辑 | 后果 |
|---|---|---|
| **准入** | `weight > maxWeight × (VIP ? 1.1 : 1.0)` 则淘汰这台车 | 太重的包裹直接派不出车 |
| **能耗** | `weightFactor = 1 + (weight / maxWeight) × 0.2`，耗电 `Δ = 里程 × 单公里耗电% × weightFactor`；要求 `Δ ≤ 90%` 且 `当前电量 − Δ ≥ 10%` | 重包裹更费电，可能连电量准入都过不了 |
| **计价** | `+ 重量 × 每公斤单价` | 越重越贵 |

> 注意：用的是**每台车自己的** `maxWeight / maxVolume / 续航 / 速度`，不是类型级硬编码；类型默认值只在机器没上报能力字段时兜底。这是 `9dca22b` 重构的重点。

### 1.3 ⚠️ Fragile（易碎）：目前是**死字段**，没有参与任何计算

**证据**：全后端仅 `RecommendationContractDto.java:49` 出现 `private Boolean fragile;`，除此之外**没有任何引用**——不加价、不限车型、不强制保价。

建议补法（低成本、且正好补上 §3 里 Amazon 那一条差异）：

```java
// 1) 加价：易碎品附加費
if (Boolean.TRUE.equals(req.getFragile())) {
    originPrice = originPrice.add(new BigDecimal("3.00"));   // 固定保价手续费
}
// 2) 限制车型：只允许地面机器人（无人机空投风险高）
// 3) 强制勾选保价 ≥ 声明价值的一定比例
```

### 1.4 ⚠️ Express（加急）：**不存在**

**证据**：`PlanType` 枚举只有 `FASTEST / BEST_VALUE / OFF_PEAK`，没有 `EXPRESS`。所谓"极速达"是靠**无人机**实现的 FASTEST，属于"选更快的载具"，不是"同载具加钱插队"。

建议补法（对应 Uber surge / Amazon 次日达那种感知）：

```java
public enum PlanType { FASTEST, BEST_VALUE, OFF_PEAK, EXPRESS }   // 新增

// EXPRESS：同车型、同路线，插队优先派车 + 加价系数
if (planType == EXPRESS) {
    originPrice = originPrice.multiply(new BigDecimal("1.5"));   // 加急 1.5 倍
    // 并按 priority 抢占 availableUnits 里电量最高的那台
}
```

## 2. 计价规则

### 2.1 费率表（`RecommendationService` 常量，与说明书 2.4 一致）

| 载具 | 起步价 | 每公里 | 每公斤 |
|---|---|---|---|
| **DRONE 无人机** | 15.00 | 1.80 | 2.00 |
| **ROBOT 机器人** | 6.00 | 0.90 | 0.80 |

### 2.2 公式

```
原价 = 起步价 + 闭环里程(站点→取件→送达→回站) × 每公里单价 + 重量 × 每公斤单价
折后价 = 原价 − 折扣
```

**折扣**：

| 情形 | 折扣 |
|---|---|
| OFF_PEAK 错峰（延后 1 小时出发） | 原价 × 15% |
| VIP 用户 | 原价 × 10% |
| VIP + 错峰（叠加） | 先减 15%，再对余额减 10% |

**时效估算**：`minutes = 闭环里程 × 0.65 ÷ 巡航速度`（0.65 是直线距离到实际路程的经验折算）。

> 一句话记忆：**无人机贵在起步价（15 vs 6）和每公里（1.8 vs 0.9），机器人便宜但慢**；所以短途轻货机器人明显便宜，长途重货两者差距缩小。

## 4. AI 增强方案（自然语言 / 客服 / 拍照 / 语音）

### 4.1 现状：前端已就绪，后端**缺人实现**

`web/src/api/ai.js` 已经写好两个调用：

```js
export async function parseOrderText(text) {          // 自然语言下单
    const { data } = await http.post('/ai/parse', { text });
    return data;
}
export async function sendChatMessage(body) {         // AI 客服
    const { data } = await http.post('/ai/chat', body);   // { message, history }
    return data;                                          // { reply, cards?, prefill? }
}
```

但**后端没有 `AiController`**（已 grep 确认），所以现在只有 `VITE_MOCK=1` 的 mock 能跑。注释里也写着：*frontend-proposed endpoint, needs a backend owner before it counts*。

### 4.2 推荐架构：复用你的 `project3/agentai`

`agentai` 是 Node + Express + LangChain + 多模型链（智谱/硅基流动兜底），天然适合当**独立的 AI 微服务**：

```
前端 /ai/parse, /ai/chat
        ↓ (axios, /api 前缀)
Java 后端 AiController（新增）
        ↓ 服务间调用（内部 HTTP，密钥不外泄）
agentai 微服务（Express + LLM）
```

为什么不前端直连 agentai：会暴露 LLM key、且跨域；由 Java 代理还能顺带做鉴权和降级。

### 4.3 agentai 侧：`/ai/parse` 结构化抽取（示意）

```js
// server/routes/ai.js
import { ChatPromptTemplate } from '@langchain/core/prompts';
import { llm } from '../llm.js';          // 你已有的多模型链

const PARSE_SCHEMA = {
  pickup: 'string', dropoff: 'string',
  weightKg: 'number', lengthCm: 'number', widthCm: 'number', heightCm: 'number',
  fragile: 'boolean',
  preference: '"fastest" | "cheapest" | "balanced"',
};

router.post('/ai/parse', async (req, res) => {
  const { text } = req.body;
  const prompt = ChatPromptTemplate.fromTemplate(`
    从下面这句下单需求里抽取字段，只输出 JSON，不要解释。
    缺失字段填 null，preference 默认 "balanced"。
    用户说：{text}
    字段：${JSON.stringify(PARSE_SCHEMA)}
  `);
  try {
    const out = await llm.invoke(await prompt.format({ text }));
    const json = JSON.parse(out.content.replace(/```json|```/g, '').trim());
    return res.json(json);                       // 200
  } catch (e) {
    // 降级：正则抠出重量/地址，保证前端永远有结果
    return res.json(regexFallback(text));
  }
});
```

> 关键是 **JSON 结构化输出 + 解析失败降级**。别让 LLM 输出直接进数据库。

### 4.4 Java 侧：代理 + 兜底（示意）

```java
@RestController
@RequestMapping("/api/ai")
@RequiredArgsConstructor
public class AiController {
    private final AiGateway aiGateway;              // 封装 RestTemplate → agentai

    @PostMapping("/parse")
    public ResponseEntity<?> parse(@RequestBody Map<String, String> body) {
        String text = body.get("text");
        try {
            return ResponseEntity.ok(aiGateway.parse(text));
        } catch (Exception e) {
            // 后端也留一手正则兜底，LLM 挂了照样能用
            return ResponseEntity.ok(RegexParser.parse(text));
        }
    }

    @PostMapping("/chat")
    public ResponseEntity<?> chat(@RequestBody Map<String, Object> body) {
        // 只做只读意图：查单、报价、解释状态；写操作一律返回 prefill 让用户自己走流程
        return ResponseEntity.ok(aiGateway.chat(body));
    }
}
```

### 4.5 语音输入（浏览器原生，零依赖）

```jsx
// 按住说话 → 文本 → 直接喂给 /ai/parse
const rec = new (window.SpeechRecognition || window.webkitSpeechRecognition)();
rec.lang = 'en-US';                       // 录的是英文地名，用 en-US
rec.interimResults = false;
rec.onresult = async (e) => {
  const text = e.results[0][0].transcript;
  const parsed = await parseOrderText(text);   // → 自动填好下单向导
  form.setFieldsValue(parsed);
};
rec.start();
```

注意：语音/摄像头都**要求 HTTPS 或 localhost**，局域网 IP 访问会拿不到权限（这点你之前在 agentai 里踩过）。

## 5. 管理员界面：看所有机器人/无人机状态

**好消息：后端数据结构已经齐全**，`AdminDashboardDto` 里有：

- 总览：`totalVehicles / idleVehicles / busyVehicles / chargingVehicles / faultVehicles / offlineVehicles`
- 每站 `vehicles[]`：`vehicleCode, vehicleType, status, batteryLevel, maxWeight, cruiseSpeed, enduranceMinutes, maxDeliverableDistanceKm, locationCode, updatedAt`
- 最近订单 `recentOrders[]`

即所需要的数据后端**已经产出**，前端直接渲染即可（现成范例：`web/src/pages/AdminDashboard.jsx`）。

### 5.1 后端：一个接口返回全部

```java
@GetMapping("/api/admin/dashboard")
public ResponseEntity<AdminDashboardDto> dashboard() {
    return ResponseEntity.ok(stationService.buildDashboard());

```

`AdminDashboardDto.VehicleItemDto` 就是一行车的数据，`locationCode` 里 `0` = 不在站内、`1/2/3` = 停在对应站点，正好用来画"哪些车在跑、哪些在充电"。

### 5.2 前端：按站点分组 + 状态徽标 + 自动刷新

```jsx
const [data, setData] = useState(null);

// SimulationScheduler 后端每 10s 推进一次，这里 5s 拉一次就够跟得上
useEffect(() => {
  const load = () => adminApi.getDashboard().then(setData);
  load();
  const t = setInterval(load, 5000);
  return () => clearInterval(t);
}, []);

const statusColor = { IDLE: 'green', IN_DELIVERY: 'blue', CHARGING: 'orange',
                      FAULT: 'red', OFFLINE: 'default' };

<Table dataSource={data?.stations?.flatMap(s => s.vehicles ?? [])} rowKey="id">
  <Column title="编号"   dataIndex="vehicleCode" />
  <Column title="类型"   dataIndex="vehicleType" />
  <Column title="状态"   dataIndex="status"
          render={v => <Tag color={statusColor[v]}>{v}</Tag>} />
  <Column title="电量"   dataIndex="batteryLevel"
          render={v => <Progress percent={v} size="small" />} />
  <Column title="最大载重(kg)" dataIndex="maxWeight" />
  <Column title="位置"   dataIndex="locationCode"
          render={v => v === 0 ? '在途' : `站点 ${v}`} />

```

配色建议：`IDLE 绿 / IN_DELIVERY 蓝 / CHARGING 橙 / FAULT 红 / OFFLINE 灰`，一眼能看出 fleet 健康度。

> 想更实时可以把轮询换成 SSE 或 WebSocket；但考虑到队友已有 `SimulationScheduler` 定时推进，轮询实现成本最低、最稳。
