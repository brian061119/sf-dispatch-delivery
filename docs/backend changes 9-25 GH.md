## 2. Database: PostgreSQL on AWS RDS

### Why PostgreSQL
The team chose PostgreSQL over MySQL mainly for PostGIS (future "nearest station/vehicle" queries in the database), stricter data validation, and transactional schema changes. The design doc (`docs/system_architecture_and_database_design.md`) was updated to say PostgreSQL.

### AWS setup
- Engine: **PostgreSQL 16** on RDS, region **us-east-2 (Ohio)**, free-tier `db.t3.micro`/`db.t4g.micro`, database name `wedelivery`.
- **Public access: Yes**, with the security group allowing **PostgreSQL / 5432** only from specific IPs (`<your IP>/32`). Each teammate who wants to connect must have their IP added.
- Connection settings live in `server/src/main/resources/application-aws.yml` (endpoint, username, password and JWT secret are stored there as defaults, by team decision — the repo is public, so the security group IP allowlist is what protects the database).

### How profiles work

| How you run it | Database used |
|---|---|
| Default (no profile) | Local in-memory **H2** in PostgreSQL mode — wiped on every restart |
| `SPRING_PROFILES_ACTIVE=aws` | **AWS RDS PostgreSQL** (shared by the team) |

In IntelliJ: *Run → Edit Configurations → WeDeliveryApplication → Environment variables* → `SPRING_PROFILES_ACTIVE=aws`.
Environment variables `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`, `DB_SSLMODE` and `JWT_SECRET` can override the defaults.

### Code changes for PostgreSQL
- `pom.xml`: MySQL driver replaced with `org.postgresql:postgresql`.
- `schema.sql`: `AUTO_INCREMENT` → `GENERATED BY DEFAULT AS IDENTITY`, `DATETIME` → `TIMESTAMP`; station names made `UNIQUE`.
- `data.sql`: H2-only `MERGE INTO ... KEY(...)` replaced by `INSERT ... ON CONFLICT DO NOTHING`, **without explicit ids** (PostgreSQL identity sequences don't advance on explicit ids, which would make the next registration fail with a duplicate key). Vehicles reference their station by name.
- `application.yml`: H2 runs in `MODE=PostgreSQL`; JWT secret configurable via `JWT_SECRET`.
- `application-aws.yml` (new): PostgreSQL URL with `sslmode=require`, `PostgreSQL10Dialect`, `ddl-auto: none` (schema is owned by `schema.sql`), small connection pool.

### Migrations for the existing RDS database
`schema.sql` uses `CREATE TABLE IF NOT EXISTS`, which does not change tables that already exist. So incremental migrations were added at the end of `schema.sql`. They are safe to run on every startup (no-ops on databases that already have the changes):

- **v1.1** — `orders.tracking_code` column + unique index.
- **v1.2** — the teammate's 8 new `vehicles` columns (`endurance_minutes`, `location_code`, `current_lat/lng`, `current_speed`, `position/status/speed_updated_at`). Vehicles that existed before the migration are backfilled as parked at their station, with default endurance per type (DRONE 30 min, ROBOT 240 min).

Both migrations have been applied to the AWS database (see §7).

## 4. Security changes

### Signup can't create admins
`POST /api/auth/register` used to accept a `role` field, so anyone could sign up as `ADMIN` (or get a free year of `VIP`). Signup now **always creates `USER`**; a `role` field in the request is ignored.

Only a developer can grant roles, directly in the database:

```sql
UPDATE users SET role = 'ADMIN' WHERE username = 'someone';
UPDATE users SET role = 'VIP', vip_expire_at = '2027-12-31 23:59:59' WHERE username = 'someone';
```

The change takes effect immediately (the role is read from the database on every request).

### Order ownership

| Endpoint | Customer who placed it | Other customer | Admin | Not logged in |
|---|---|---|---|---|
| `GET /api/orders/{orderNumber}` | 200 | 403 | 200 | 401 |
| `GET /api/orders/{orderNumber}/tracking` | 200 | 403 | 200 | 401 |
| `PATCH /api/orders/{orderNumber}/confirm-receipt` | 200 | 403 | 403 | 401 |
| `GET /api/orders` | own orders only | own orders only | own orders only | 401 |

### 401 vs 403
Previously every rejection was 403. Now **401** = not logged in, **403** = logged in but not allowed (`HttpStatusEntryPoint` in `SecurityConfig`).

### Dispatch write endpoints are admin-only
The teammate's new write endpoints under `/api/dispatch/` were reachable without any login. They now require **ADMIN**:

- `POST /api/dispatch/stations/import`
- `POST /api/dispatch/vehicles/import`
- `POST /api/dispatch/vehicles/{code}/telemetry`
- `POST /api/dispatch/vehicles/{code}/location`
- `POST /api/dispatch/simulate/tick`

Still public: all `GET` under `/api/dispatch/**`, `/api/stations/**`, `/api/vehicles/**`, and `POST /api/dispatch/quote`.

## 5. Public tracking code

Order numbers look like `SFORD` + timestamp + 3 random digits, so they are easy to guess. Anyone could track someone else's delivery (and see the drop-off location).

- Every new order gets a random **16-character tracking code** (e.g. `AL3E8TNAUEQTSTCN`; no `0/O/1/I`; ~10²⁴ possibilities).
- The code is returned by `POST /api/orders` and `GET /api/orders` (`trackingCode` field) and in the order detail.
- **Public tracking:** `GET /api/tracking/{trackingCode}` — no login, read-only (GET only). Order numbers and wrong codes → 404.
- **Owner tracking:** `GET /api/orders/{orderNumber}/tracking` — login required (owner or admin).
- Both return the same response shape (the contract's tracking response).

`api-contract.md` was updated accordingly.

## 6. Error responses

New `exception/GlobalExceptionHandler` + `ResourceNotFoundException`. Errors are returned as JSON:

```json
{ "timestamp": "...", "status": 404, "error": "Not Found", "message": "Order not found: SFORD..." }
```

| Situation | Before | Now |
|---|---|---|
| Order / tracking code not found | 500 | **404** |
| Wrong password or unknown user at login | 500 | **401** "Invalid username or password." (same message for both, so usernames can't be probed) |
| Username / email already registered, missing field | 500 | **400** |
| No free vehicle at the station | 500 | **409** |
| Not allowed | 403 (empty body) | **403** with message |

Payment failures still return 500 — the payment error format is still TBD in `api-contract.md`.
