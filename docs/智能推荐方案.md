## 一、结论先行

**现在的推荐不是"智能推荐"，是"可行方案枚举 + 事后贴标签"。**

它把"能不能做"（准入筛选）做得相当扎实，但完全没做"哪个最适合你"（排序与匹配）。
`score` 字段只有 60 / 80 / 100 三个值，且与用户无关——**两个不同偏好的用户提交同样的地址，会得到完全相同、同样排序的三个方案。**

好消息是：**缺的这一层已经写好并跑通了单测**（`PlanScoringService`），后端只需要替换 `generateContractRecommendations` 里那一行 score 计算，不需要动准入逻辑、不需要动价格公式。

## 二、现状：哪些写得好，哪些是空的

### 做得好，必须保留（不要重写）

| 部分 | 代码位置 | 为什么好 |
|---|---|---|
| 三重准入筛选 | `RecommendationService:151-182` | 载荷（weight/volume，VIP 有 1.1 倍容忍）、续航（`maxDeliverableDistanceKm × 0.9` 安全系数）、电量（载重加权能耗 + 10% 冗余）——写得比多数课程项目细 |
| 服务端重算防篡改 | `resolveContractCandidate:322` | 下单时用 `candidateId` 重算一遍，不信任客户端价格。这是契约定下的红线，实现是对的 |
| 价格公式 | `buildOption:202` | `base + 距离×perKm + 重量×perKg`，两套定价常量清晰分离 |
| 选站 | `selectBestStation:105` | 取件点最近站点，合理的一级近似 |

### 空的：推荐系统该有的四件事一件都没做

| 缺什么 | 证据 | 后果 |
|---|---|---|
| **① 用户意图** | `priority` 字段在 DTO 里定义了（`RecommendationContractDto.Request:23`），**全后端 grep 无任何读取处** | 用户选了 EXPRESS（加急），系统不知道 |
| **② 个性化** | 打分只依赖候选之间的相互比较 | 所有人拿到同样排序 |
| **③ 多目标权衡** | 没有时间/成本/可靠性的加权 | 回答不了"哪个最符合**我**" |
| **④ 可解释性** | `CandidateDto` 无 reason 字段 | UI 上那个 ★Recommended 是盲信，讲不出为什么 |

### 三个具体的坏味道

**坏味道 1：`score` 是枚举出来的，不是算出来的**

```java
// RecommendationService:296
double score = (isFastest ? 50.0 : 30.0) + (isCheapest ? 50.0 : 30.0);
```

只有 60 / 80 / 100 三种取值。`isFastest` 和 `isCheapest` 又经常**同时成立**（短距离时机器人常常又快又便宜），导致 100 分并列——UI 的 ★Recommended 徽章实际是随便挑一个。

**坏味道 2：OFF_PEAK 是硬编码的假错峰**

```java
// RecommendationService:253
LocalDateTime scheduledStart = LocalDateTime.now().plusHours(1);   // 永远延后 1 小时
BigDecimal offPeakDiscount = originPrice.multiply(OFF_PEAK_DISCOUNT_RATE);  // 永远 85 折
```

**不看当前是不是高峰。** 凌晨 3 点下单，系统照样推荐你"延后一小时享 8.5 折"——而那个时段根本不存在拥堵。`PlanType.OFF_PEAK` 这个枚举值本身是对的，只是没接真实的时间信号。

**坏味道 3：超重是死胡同**

`evaluate()` 返回 `null` → `candidates: []`。用户填 4kg（超出无人机 3kg 上限）时，Step 3 直接空白，没有任何提示。这不是推荐问题，是体验缺陷，顺手该修。

## 三、改造方案：把"贴标签"换成"效用打分"

### 核心公式

```
utility(c) = 1 − wTime × normTime(c) − wCost × normCost(c) − wRisk × risk(c) − deadlinePenalty(c)
```

| 项 | 含义 | 数据来源 |
|---|---|---|
| `normTime` / `normCost` | min-max 归一化到 0–1（时间和钱量纲不同，必须先归一） | 候选集内部相对比较 |
| `risk(c)` | 稀缺风险：`availableUnits ≤ 1` → 1.0；`== 2` → 0.5；更多 → 0 | **对应真实痛点**：只有 1 台空闲时，报价到下单之间它可能被订走，这正是用户遇到 409 的原因 |
| `deadlinePenalty` | 超出用户要求时间时惩罚，上限 0.6 | 用户自然语言里的时间要求 |
| `wTime/wCost/wRisk` | 权重，归一化后和为 1 | **由用户意图决定，这是 AI 的入口** |

### 为什么权重来自"意图"而不是硬编码

同一个候选集，权重不同 → 赢家不同。已验证（单测 `PlanScoringServiceTest`）：

| 意图 | 第一名 | 说明 |
|---|---|---|
| 最快（`wTime=0.75`） | 无人机 20 min / ¥30 | |
| 最省（`wCost=0.75`） | 错峰 105 min / ¥7 | 便宜 ¥8 值得多等 85 分钟 |
| 均衡（`0.45/0.45`） | 机器人 45 min / ¥15 | |
| 均衡 **+ 要求 30 分钟内到** | **无人机** | 加了 deadline 后，赢家从机器人翻转为无人机 |

最后一行是这个设计的价值所在：**deadline 能把排序翻过来**，而现在的 `score` 对"用户 5 点前必须到"这件事完全无感。

### 顺带产出：推荐理由

`Scored.getReason()` 自动生成一句英文说明，可直接进 UI：

```
"Fastest option, arrives in 20 min; arrives 10 min before your deadline"
"Cheapest option, about 85 min slower; only 1 vehicle left"
"Balanced price and speed; misses your 30-min deadline"
```

这是推荐系统的**可解释性**，也是 Final Review 里"AI 功能是否可信"的得分点——能讲出理由的推荐，和黑箱排序，评审一眼就能分开。

## 四、Jev 放在哪：只让它决定权重，不让它碰价格

### 一句话架构原则

> **LLM / Jev 负责理解用户想要什么；后端规则负责算出能做到什么。价格与可行性永远由规则决定。**

这条原则同时满足三件事：契约定下的"定价归后端"、AI 的可解释性、以及退化安全。

### Jev 的具体用法（`POST https://api.typesafe.ai/v1/systemone`）

Jev 不生成文本，只在你给定的选项里做 choice / score / noul。用它来**从用户那句自然语言里提取意图权重**：

```json
{
  "model": "jev-1.13.0",
  "state": "用户原话: 把两本教材从 SF State Library 送到 701 Mission，5 点前必须到，易碎\n可用方案: [A] 无人机 20min ¥30 (剩2台) [B] 机器人 45min ¥15 (剩3台) [C] 错峰 105min ¥7",
  "questions": {
    "priority":  { "type": "choice", "instructions": "用户最在乎哪一项?",
                   "criteria": { "speed": "提到加急/尽快/ASAP", "cost": "提到便宜/省钱/不着急",
                                 "reliability": "提到易碎/贵重/稳妥", "balanced": "没有明确倾向" } },
    "urgency":   { "type": "score", "instructions": "紧急程度?",
                   "criteria": ["完全没提时间", "提到今天/某个时间点", "提到必须/立刻/ASAP"] },
    "has_deadline": { "type": "noul", "instructions": "是否给出了明确的送达时间要求?" },
    "time_flexible": { "type": "noul", "instructions": "是否接受延后配送以换取折扣?" }
  }
}
```

响应到权重的映射（后端做，纯查表，无 AI）：

| Jev 输出 | 映射到的 Intent |
|---|---|
| `priority=balanced` | `Intent(0.45, 0.45, 0.10)` |
| `priority=speed` | `Intent(0.75, 0.15, 0.10)` |
| `priority=cost` | `Intent(0.15, 0.75, 0.10)` |
| `priority=reliability` | `Intent(0.20, 0.20, 0.60)` |
| `has_deadline` 为真 + `urgency` 高 | 追加 `deadlineMinutes`（由 LLM 或直接让用户选） |
| `time_flexible` 为真 | 才把 OFF_PEAK 纳入展示（**修掉坏味道 2**） |

### 为什么不直接用 Jev 从候选里选

| 做法 | 问题 |
|---|---|
| ❌ `choice` 直接选 3 个候选之一 | 不可复现、无法单测；Jev 拿不到价格计算过程，只能凭 state 里的摘要猜；挂了就全盘崩 |
| ❌ 让 AI 输出价格或时间 | 违反契约红线，**这是评审最忌讳的** |
| ✅ AI 输出权重 + 规则算分（本方案） | 价格可复现可测试；AI 挂了退化为 `balanced()`，系统照常工作 |

可选进阶：**AI 复核 tie-break**。规则排序后若前两名分差 < 0.05，让 Jev 在两者间 `choice` 一次，附带 confidence；confidence 低于 0.6 时以规则结果为准。这是诚实的"人机协同"，也很好讲。

### 接入方式（技术细节）

- **无 webflux**，`WebClient` 不可用 → 用 `RestTemplate`（`spring-boot-starter-web` 已带，零新依赖）
- API key 必须放后端配置（`application.yml` 或环境变量），**绝不能进 `VITE_*`**（会被打进前端 JS 泄露）
- 请求超时设 1.5s，失败/超时/解析异常一律 `catch` 后回退 `balanced()`
- 成本：Jev 输入 $0.042/百万 token、输出免费，这类短调用约 $0.000013/次，可忽略

## 五、Decision Matrix（按 Lesson41 格式）

| Factors | A. 保持现状 | **B. 规则打分 + AI 定权重** ★ | C. AI 直接选方案 |
|---|---|---|---|
| 个性化 | L（无） | **L（权重随用户变）** | L |
| 可解释性 | L（无理由） | **L（reason 可生成）** | M（AI 说不出依据） |
| 可测试性 | — | **L（纯函数，9 个单测已过）** | L（不可复现） |
| 价格可信度 | L | **L（AI 不碰钱）** | S（风险高） |
| 退化安全 | L（无 AI 依赖） | **L（AI 挂 → balanced）** | S（AI 挂 → 全崩） |
| 实现成本 | 0 | **M（打分已写好，只需接线）** | M（但需重构信任模型） |
| KISS | L | **M** | M |
| 契合老师提的 Jev | L | **L（教科书用法）** | L |

**选 B。** 理由：它在"有 AI"和"系统可信"之间取到平衡点，且 Phase 0 不依赖任何 AI 就能先落地一半。

## 六、落地步骤

### Phase 0 —— 不加 AI，立刻能做（建议 Week2 内）

1. 在 `generateContractRecommendations` 里把 score 计算换成：
   ```java
   List<Scored> ranked = PlanScoringService.rank(plans, PlanScoringService.fromPriority(priority));
   // ranked.get(0) 即推荐项，用 .getScore() 填 score、.getReason() 填 reason
   ```
   `priority` 字段已经传到后端了，只是没人读——**这一步零新增接口**。
2. `CandidateDto` 加两个字段（向后兼容，前端可选读）：
   ```java
   private Integer matchScore;   // 0..100 连续值
   private String reason;        // "Cheapest option, about 85 min slower"
   ```
3. 前端 Step 3 把 `reason` 显示在 ★Recommended 卡片下方。

### Phase 1 —— 接 Jev（Week3，需 key）

4. 新增 `AiIntentService`（`RestTemplate` + 超时 + 退化），输入用户自然语言，输出 `Intent`。
5. `RecommendationContractDto.Request` 加 `userNote` 字段（可选），前端在 Step 1 提供一个"或用一句话描述"输入框。
6. `time_flexible` 为真才展示 OFF_PEAK（修坏味道 2）。

### Phase 2 —— 可选（有余力才做）

7. 超重/无可用载具时给**补救建议**（拆单 / 换站点），修坏味道 3。
8. 前两名分差过小时用 Jev tie-break（带 confidence 与规则兜底）。

## 七、红线（不要破）

1. **AI 永远不输出价格、时间、可行性**——只输出权重与理由语气。
2. **所有 AI 调用必须有规则退化路径**，否则 demo 现场 API 挂 = 全盘崩。
3. **`score` 字段保持 0–100 区间**，前端 `★Recommended` 的现有逻辑不用改就能兼容。
4. 若要写进 Design Doc 或对外讲，**AI 功能必须标注是否已上线**（Phase 1 之前只能说"已设计+单测通过，待接入"）。
