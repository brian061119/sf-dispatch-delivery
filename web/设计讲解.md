# WeDelivery 前端设计讲解（Yiting Qi）

> 用途：跟老师 / 队友讲清楚**每一层怎么设计的、为什么这么设计**。
> 结论先行，细节按层展开；被提问时直接查文末 FAQ。
> **API 的 URL + method 以团队仓库 `api-contract.md`（2026-09-21 确认版）为准**，前端代码已全部对齐它。

---

## 0. 一句话总览

React 单页应用，分五层：**页面(pages) → 状态(store) → 接口(api) → 基建(lib) → 契约(types)**，
组件只跟 store 和 api 函数说话，**任何文件不直接碰 axios / localStorage / 后端路径细节**。

```
┌────────────────────────────────────────────────────┐
│ pages/  7 个页面（按 owner 分工）                     │
│ components/  6 个公共组件（设计系统）                  │
├────────────────────────────────────────────────────┤
│ store/   zustand × 3：auth(会话) wizard(下单草稿)     │
│          orders(订单列表缓存)                         │
├────────────────────────────────────────────────────┤
│ api/     按契约分组的接口函数（auth/recommendation/    │
│          order/tracking/station/ai）                 │
├────────────────────────────────────────────────────┤
│ lib/     http.js(唯一 axios 实例+JWT+401) auth.js     │
├────────────────────────────────────────────────────┤
│ types/api.js  前后端契约（JSDoc @typedef，           │
│               镜像 api-contract.md）                  │
└────────────────────────────────────────────────────┘
              │  所有请求统一走 /api 前缀
              ▼
        vite proxy → 后端 :8080
```

## 1. 技术选型与理由

| 选择 | 为什么 |
|---|---|
| **React 19 + JavaScript** | 全组 JS 最熟，与课程项目（social-ai）栈对齐，上手零成本 |
| **Vite 6**（不是 CRA） | CRA 已停止维护；Vite 启动 <1s、HMR 快，是现行标准 |
| **antd v6** | 课程项目同款组件库，Form/Table/Steps/Card 开箱即用，线框图直接映射 |
| **zustand 5**（不是 Redux / Context） | 见 FAQ 1 |
| **axios** | 拦截器机制是 JWT/401 统一处理的关键；fetch 要自己包一层 |
| **react-router-dom 7** | 声明式路由 + 守卫（RequireAuth） |
| **react-leaflet + OpenStreetMap** | 真实地图、免费无 key（Google Maps 要绑信用卡） |
| ~~TypeScript~~ → **JSDoc @typedef** | 2026-09 从 TS 转 JS。契约不丢：`types/api.js` 里 `@typedef` 保留全部类型信息，编辑器照样有悬浮提示，但**运行时零成本、构建链零依赖** |

## 2. API 设计（重点：为什么有 `/api` 前缀）

### 2.1 端点一览（全部来自 api-contract.md 确认版）

| 方法 | 路径 | 请求体 → 响应 | Owner | 前端调用处 |
|---|---|---|---|---|
| POST | `/api/auth/register` | RegisterRequest(TBD) → {token, user} | Ziyuan | `api/auth.js` |
| POST | `/api/auth/login` | LoginRequest → {token, user} | Ziyuan | `api/auth.js` |
| POST | `/api/auth/logout` | —（TBD：是否服务端失效） | Ziyuan | `api/auth.js` |
| GET | `/api/auth/me` | — → user（TBD，预留） | Ziyuan | `api/auth.js` |
| POST | `/api/recommendations` | {pickup, dropoff, package, priority} → {candidates[]} | Zihang | `api/recommendation.js` |
| POST | `/api/orders` | {candidateId, …, paymentMethodId} → 201 {orderId, status, …} | Zihang | `api/order.js` |
| GET | `/api/orders` | — → {orders[]} | Zihang | `api/order.js` |
| GET | `/api/orders/:id` | — → 详情（body TBD，前端防御式渲染） | Y | `api/order.js` |
| PATCH | `/api/orders/:id/confirm-receipt` | — → {orderId, status: DELIVERED} | Y | `api/order.js` |
| POST | `/api/orders/:id/review` | {rating, comment, damageReported} → {reviewId} | Y | `api/order.js` |
| GET | `/api/orders/:id/tracking` | — → {status, vehicleType, currentLat/Lng, estimatedArrival} | Yuning | `api/tracking.js` |
| GET | `/api/stations` | — → 站点数组（TBD） | Zihang(地图) | `api/station.js` |
| POST | `/api/ai/parse` | {text} → 草稿（**P1 提议，未入契约**） | 待认领 | `api/ai.js` |

风格是**资源式 REST**：名词做路径（`/orders`），HTTP 方法表动作（GET 查 / POST 创建 / PATCH 局部更新），
子动作挂在资源下（`/orders/:id/confirm-receipt`、`/orders/:id/tracking`）。

契约里还有两个值得讲的设计：
- **下单=支付+创建一次调用**（embedded payment）：`POST /api/orders` 带上 `paymentMethodId`，后端一次完成扣款+建单，
  前端成功后直接跳追踪页，没有支付回调页。真实项目里 `paymentMethodId` 应该来自 Stripe Elements 的 token 化，**绝不传原始卡号**。
- **`isFastest` / `isCheapest` 由后端算**：推荐打分的口径（权重、规则）集中在后端 `RecommendationService`，
  前端只展示标签——这样算法改规则不用发前端新版。

### 2.2 为什么要加 `/api`？——它是契约的一部分，也是 vite 代理的"识别特征"和部署的"反代锚点"

首先：**团队确认版契约里每个端点都带 `/api`**，前端照契约写，这件事本身不需要争论。
但就算契约没规定，我们也还是会加，原因是三个工程收益：

前端代码里所有请求写相对路径 `/api/...`，浏览器实际打的是**同源** `localhost:3000/api/...`，
由 vite dev server 按前缀转发到后端 `localhost:8080`（`vite.config.js` 的 proxy 段）：

```js
// vite.config.js
proxy: { '/api': { target: process.env.VITE_API_PROXY_TARGET || 'http://localhost:8080', changeOrigin: true } }
```

1. **开发态零 CORS**。浏览器看到的是同源请求，不触发跨域；后端开发期完全不用配 CORS。
2. **代理规则只要一条**。Vite 的 proxy 是**按路径前缀匹配**的。有了共同前缀 `/api`，一条规则覆盖全部端点；
   没有前缀就得把 `/auth`、`/orders`、`/recommendations`……逐个列出来，每加一个端点改一次构建配置。
3. **生产部署一行 nginx 搞定**。`npm run build` 后是纯静态文件，没有 vite proxy。上线时静态资源和后端同域部署，
   nginx 把 `/api` 反代到后端即可；换后端地址改 `VITE_API_BASE_URL` 环境变量（`lib/http.js` 里读），代码不动。

### 2.3 对比：我其他课程项目为什么都没加 `/api`？

不是所有项目都该加，**取决于 dev server 的代理机制和部署形态**：

| 项目 | 后端 | API 路径风格 | 为什么不需要 `/api` |
|---|---|---|---|
| **OnlineOrder** | Spring Boot | `/login`、`/orders`… 无前缀 | 前端 build 产物由 **Spring 自己 serve**，天然同源，不需要代理 |
| **social-ai** | Go on GAE | `/upload`、`/search`… 无前缀 | 前端部署后直连**后端完整域名 URL**（构建时注入 `REACT_APP_API_DOMAIN`），跨域由后端 CORS 解决 |
| **agentai** | Express | `/chat`、`/upload`… 无前缀 | CRA 的 `"proxy"` 字段是**兜底转发**：凡是不认识的请求都转给后端，不需要特征前缀 |
| **WeDelivery**（Leluth 参考仓库） | Spring + Tomcat | `/getorder`、`/cancelcart`… 动词式、无前缀 | 前后端打同一个 war 包部署，同源 |
| **FlagCamp（本项目）** | Spring Boot | `/api/orders`… 名词式 REST | ① 团队契约如此；② Vite proxy 按前缀匹配需要特征；③ 前后端分开部署时的反代锚点 |

一句话给老师：**加不加 `/api` 不是对错问题，是"dev server 怎么识别 API 请求 + 部署时怎么分流"的工程问题。
CRA 兜底转发、Spring/Tomcat 同源 serve 的项目不需要；Vite 按前缀代理、前后端分开部署的项目加了最省事。本项目契约直接规定了它。**

### 2.4 对比：WeDelivery（Leluth）的 API 设计风格

Leluth 的仓库是**动词式 RPC 风格**：`@RequestMapping("/getorder")`、`/cancelcart`、`/tmpcart`……
我们和团队契约都是**名词式 REST**：`GET /api/orders`、`PATCH /api/orders/:id/confirm-receipt`。

| | 动词式（WeDelivery） | 名词式 REST（本项目/团队契约） |
|---|---|---|
| 路径语义 | 动作塞在路径里，`/getorder` 是 POST 还是 GET 要看注解 | 名词 + HTTP 方法，看路径就知道干嘛 |
| 端点膨胀 | 每个动作一个新路径 | 同一资源的动作收敛在资源下 |
| 业界主流 | 偏老式（RPC 遗风） | 主流，讲出去更专业 |

## 3. 状态设计：为什么是这三个 store

| store | 管什么 | 为什么独立 |
|---|---|---|
| `auth` | token / username / login / signup / logout | 会话是全 app 级、变化极少；创建时从 localStorage **水合**，刷新不掉线；logout 先尽力调契约端点再清本地（TBD 是否服务端失效） |
| `wizard` | 下单草稿（pickup/dropoff/pkg/priority/candidates/selected） | 下单四步共享一份草稿；**`prefill()` 合并语义**是 AI 下单的关键（见下） |
| `orders` | 订单列表 + loading + `refresh()` | Dashboard 和 History 共用一份缓存；下单成功后 `refresh()` 一次两页同步 |

**"AI drafts, wizard verifies"（AI 起草，向导核实）**——本项目最核心的一个设计决策：

Dashboard 的 AI 一句话下单**不直接创建订单**。解析返回一份可能有缺失的草稿，
用 `wizard.prefill()` **合并**进下单草稿（AI 的 `itemName` 映射到契约包裹的 `description`），
然后跳到向导第 1 步，由用户在四步流程里**逐项确认/补全**后才提交。
理由：LLM 解析不可信（重量、易碎可能漏），直接下单会出错单；让 AI 只当"填表助手"，人做最终确认。
即使解析失败也优雅降级：提示一句，照样跳进空白向导手动填。
（注意：`/api/ai/parse` 是前端为 P1 提议的端点，**不在确认版契约里**，需要后端认领。）

## 5. FAQ（被提问时查这里）

1. **为什么 zustand 不用 Redux？** 三个 store 各 20 行；Redux 的 action/reducer/dispatch 样板对这个规模是杀鸡用牛刀。
   不用 Context 是因为订单轮询 5s 一次高频更新，Context 会让整棵组件树跟着重渲染，zustand 的 selector 订阅只重渲染用到的组件。
   而且对队友最友好：会 `useState` 就会 zustand。
2. **JWT 为什么存 localStorage？** 课程项目的务实选择，简单、刷新不掉线。生产更推荐 httpOnly cookie（防 XSS 读 token），
   但需要后端配合 Set-Cookie——这是**已知的取舍**，被问到主动承认。
3. **追踪为什么轮询不用 WebSocket？** 契约里 WS `/api/ws/orders/:id` 明确标注为可选 stretch。
   5s 轮询 20 行代码、后端零改动；WebSocket 要维护长连接、鉴权握手、断线重连，P0/P1 不划算。
4. **下单四步为什么是一个路由不是四个？** 四步共享一份草稿。拆四个路由，草稿就得塞 URL 或后端暂存；
   合并成 `/order/new` 一个路由 + Steps 组件，回退上一步数据不丢，线框图 04–07 本来就画的是一个流程。
5. **详情和追踪为什么拆两个页面？** 职责不同：详情=静态信息+签收+评价（Y），追踪=实时地图+时间线（Yuning）。
   **分工按页面切分，两人永远不改同一个文件**；两页通过 `Live tracking →` 互跳，用户体验上是一体的。
6. **为什么从 TS 转回 JS？** 对齐课程栈（social-ai），全组 JS 最熟；类型契约用 JSDoc `@typedef` 保留在 `types/api.js`，
   编辑器提示不丢，构建链还少了 tsc 依赖。
7. **支付为什么不传真实卡号？** 契约设计就是 `paymentMethodId`（token 化，真实项目走 Stripe Elements）。
   我们 mock 也只发 `mock_card_<后4位>`——**原始卡号永远不过我们服务器**（PCI 合规常识），这个习惯先养成。
8. **AI 解析为什么不直接下单？** 见 §3："AI drafts, wizard verifies"。
9. **签收按钮为什么 IN_TRANSIT 就能点？** 契约是 4 态模型（PENDING/IN_TRANSIT/DELIVERED/CANCELLED），
   confirm-receipt 直接把状态翻成 DELIVERED——也就是说契约里"已送达待签收"没有独立状态。
   这是否符合产品直觉已列入交接文档待确认清单；前端逻辑跟着契约走。
10. **线框图里的取消订单按钮去哪了？** 确认版契约**没有取消端点**。按钮在 Tracking 页以 TODO 注释暂存，
    等后端加端点后恢复——这是"前端不发明契约没有的端点"原则的体现。
